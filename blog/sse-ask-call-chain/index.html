从 Beego 到 SSE：WebAgent 多维问答调用链设计

jessy 2026年8月6日 #webagent#backend#architecture#sse#beego#rag#mcp

沿一次请求的真实时间线，拆解 WebAgent 多入口问答服务中的身份归一化、会话持久化、RAG、MCP、并发控制与 SSE 终态。

面向开发者设计一个 Agent 问答服务时，真正困难的通常不是“调用一次大模型”，而是如何让不同身份、不同知识范围、不同工具权限和不同会话策略，共用一套稳定的运行时。

本文以 WebAgent 的三个 SSE 接口为例：

  • GET /api/sse/ask
  • GET /api/sse/tenant_ask
  • GET /agent/sse/ask

我们按一个请求真实发生的时间线，从 Beego HTTP 路由注册讲到身份归一化、会话持久化、缓存、RAG、MCP 工具调用、并发控制和 SSE 终态。文中的模块名与代码都是通用化设计示例，可以直接迁移到其他 Go Web 框架或 Agent 系统。

1. 三个入口，不是三个 Agent

这三个接口名字相近，但服务对象不同：

入口 主要调用方 身份来源 会话模式 知识范围 工具范围
/api/sse/ask 公开页面、轻量问答 匿名或弱身份 单轮或临时上下文 平台公共知识 默认关闭
/api/sse/tenant_ask 已登录租户用户 可信网关注入的租户和用户身份 持久会话 平台知识 + 当前租户知识 按用户权限动态授权
/agent/sse/ask 服务端集成、自动化任务 API Key 持久会话 平台知识 + Key 所属租户知识 按 Key scope 精确授权

一种容易失控的实现，是为每个入口复制一套“检索、模型、工具、流输出”逻辑。这样做很快会出现三个版本的事件协议、缓存规则和异常处理。

3. 启动阶段：先构造组合根

路由注册之前，应用需要把所有共享依赖装配好。这个启动层通常称为组合根，它只负责创建对象和建立依赖关系，不处理业务请求。

这样做有三个收益：

  • Handler 不直接创建数据库、Redis 或模型客户端，便于测试和替换。
  • 三条入口共享同一个 Runtime，行为差异由策略表达。
  • 缓存、鉴权、检索、工具调用都有清晰的所有权，不会散落在 HTTP 层。

这里特意把 ToolCatalog、ToolAuthorizer 和 ToolExecutor 拆开。如果只提供一个 CallTool 接口，Runtime 很容易把“工具已经注册”误认为“当前用户可以调用”。拆开以后，目录负责发现，权限服务负责决策，执行器只接收已经授权的调用，三个阶段都可以独立测试和审计。

基础设施也不应在 Handler 中临时创建。数据库连接池、Redis 客户端和模型客户端通常都需要复用；每次请求重新创建不仅增加延迟，还会放大连接数，并让资源关闭时机变得不可控。

5. 请求归一化：让运行时看不到 HTTP 差异

三个接口的 header、query 和鉴权方式不同，但进入 Runtime 后应该变成同一种请求：

这里最重要的是 Principal 和 AccessPolicy 分离：

  • Principal 描述调用者是谁。
  • AccessPolicy 描述这次请求允许使用什么能力。
  • Runtime 只消费可信的归一化结果，不再读取原始 HTTP header。
  • 租户 ID、用户 ID、数据范围不能由模型或工具参数自行提供。

这个边界解决的是“可信数据从哪里来”。如果 Runtime 到处读取 header，它就同时承担 HTTP 解析、身份校验和任务编排，任何新入口都可能形成一套略有不同的安全规则。归一化后，Runtime 只面对一种稳定输入，鉴权测试也能集中在接入层完成。

AskStreamer 返回只读 channel，则进一步明确了事件所有权：Runtime 决定何时生产和关闭事件，SSE Transport 决定如何编码、Flush 和处理客户端断连。二者不会互相调用对方的内部方法。

6. 第一条链路：/api/sse/ask

公共入口强调低门槛和低状态。它的处理过程可以拆成七步：

  1. 校验 query、语言、时区等基础参数。
  2. 生成或接收 request_id，用于日志关联。
  3. 构造 guest principal。
  4. 应用公共策略：只允许平台知识检索，默认关闭 MCP 和文件任务。
  5. 如果提供临时会话标识，可以从 Redis 读取短期上下文；它不等同于持久会话。
  6. 进入统一 Runtime，完成 RAG 和模型流式生成。
  7. 模型结束后直接发送 done。

公共入口即使允许短期上下文，也应该明确限制：

  • Redis 只保存带 TTL 的临时历史。
  • 不能依靠客户端提交的租户 ID 扩大检索范围。
  • 不创建权威的 conversation/message 记录。
  • 不提供需要业务身份的 MCP 工具。

7. 第二条链路：/api/sse/tenant_ask

租户入口通常位于登录网关之后。网关完成登录态校验，再向内部服务注入身份，例如：

Handler 收到请求后：

  1. 校验租户和用户标识。
  2. 构造 tenant_user principal。
  3. 创建或校验持久会话。
  4. 调用 PrepareTurn 做幂等检查、会话加锁和消息占位。
  5. 把已完成的历史消息传给 Runtime。
  6. Runtime 在“平台 + 当前租户”范围内检索。
  7. MCP 工具先发现、再授权、最后调用。
  8. 模型生成期间持续输出 SSE。
  9. 将 assistant 消息从 streaming 更新为终态。
  10. 刷新历史缓存后发送 done。

这里的 delegated credential 只用于后续权限服务验证，不应被当作租户身份本身。租户身份必须来自已经建立信任关系的网关。

11. 会话持久化在哪里发生

持久化不是最后一次性保存，而是分为三段：

11.1 生成前

  • 创建或确认 conversation。
  • 创建 user message。
  • 创建 assistant placeholder。
  • 保存 request id。
  • 读取历史。

这一步失败时，不应该调用模型。

11.2 生成中

  • 文本增量只通过 SSE 发送。
  • 可以周期性保存 checkpoint，但不要每个 token 写数据库。
  • 工具调用、耗时、用量等先收集在当前 turn context。
  • 客户端断开时通过 context 取消后续检索、模型和工具任务。

11.3 生成后

  • 把 assistant 内容和 metadata 写入数据库。
  • 将 assistant 状态改为 completed。
  • 更新 conversation 的 history version。
  • 持久化文件任务或其他投影的最终状态。
  • 刷新或失效 Redis 历史缓存。
  • 最后发送 done。

如果异常退出，应把 placeholder 更新为 failed、canceled 或可恢复的 stale，避免会话里永久存在“正在生成”的消息。

缓存只包含完整的 user/assistant 问答对，不包含 streaming 或 failed 消息。读取时先比对数据库中的 history_version：

  • 版本一致：直接使用缓存。
  • 版本不一致或不存在：从数据库重建并回填。

  • Redis 命中但数据库版本不匹配：丢弃缓存，不能相信旧历史。

14. SSE 事件协议：只有一个写协程

一套可观测的事件协议可以包含：

事件 含义
turn_start 托管会话已创建本轮消息
route Runtime 选择了 RAG、工具或文件任务
retrieval_start 开始检索
retrieval_done 检索完成
tool_candidates 当前可见工具集合
tool_start 开始调用某个工具
tool_done 工具调用完成
generate_start 模型开始生成
delta 文本增量
usage token 或计费信息
error 本轮错误
done 客户端可见终态

无论内部有多少 goroutine，都只允许一个 goroutine 写 http.ResponseWriter：

这样可以避免并发写造成事件交叉、JSON 截断和 Flush 顺序混乱。http.ResponseWriter 通常不承诺并发安全；即使某个实现碰巧没有数据竞争，也无法保证 tool_start、delta 和 done 的业务顺序。

单 Writer 并不意味着内部只能串行工作。检索器、模型回调和工具协程可以并发生产 AskEvent，channel 负责线程安全地汇合，Writer 再把内部并发收敛为一条有序网络流。

事件通道应该有界。生产者快于客户端时，需要明确背压策略：

  • 关键事件和 delta 默认阻塞等待，保持顺序与完整性。
  • 高频可丢弃遥测使用独立通道，不要挤占业务事件。
  • 设置最大排队长度和写超时，防止慢客户端无限占用内存。
  • 客户端断开后立即取消 request context。

15. 并发处理：四个层次分别解决

“支持并发”不是简单地多开 goroutine。一个多租户 Agent 服务至少要处理四类并发。

15.1 API Key 限流与并发槽

  • 每分钟请求数。
  • 当前活跃请求数。

TTL 只是崩溃兜底，不等于正常释放。请求结束仍应主动递减；更严格的实现可以为每个活跃请求保存独立 lease token，再通过集合数量计算并发，避免单纯计数器被重复释放。

15.2 同一会话串行，不同会话并行

同一 owner 下的同一 conversation 应串行处理：

获取使用带过期时间的 SET NX。释放时不能直接 DEL，而要执行“value 仍等于我的 token 才删除”的 Lua 逻辑，防止旧请求误删已经续租或重新获取的锁。

随机 token 在这里相当于锁的所有权证明。仅比较 key 不够，因为 key 对同一会话始终相同。对于可能超过锁 TTL 的长回答，还需要定时续租；续租同样必须先比较 token，再执行 PEXPIRE。续租失败时应停止继续调用有副作用的工具，并让数据库状态机接管恢复。

数据库事务和行锁是第二道防线。即使 Redis 锁因超时失效，数据库中的唯一 request id、会话版本或 FOR UPDATE 仍应阻止重复 turn。

不同 conversation 没有顺序依赖，可以并行执行。

15.3 request id 幂等

客户端为每一轮提供稳定的 request_id，服务端建立唯一约束：

相同 request id 再次请求时：

  • 已完成：重放已经持久化的结果。
  • 仍在生成：返回“正在处理”，或重新订阅事件。
  • 已失败且允许重试：显式创建 retry attempt，不能静默重复工具副作用。
  • 超过最大生成时间：把旧 turn 标记为 stale，再按策略恢复。

幂等不仅避免重复模型计费，更重要的是避免重复创建工单、重复发消息等工具副作用。对有副作用的 MCP 工具，还应把 turn request id 派生为工具级 idempotency key。

15.4 同一轮多个工具并发

模型可能一次返回多个互不依赖的 tool calls。可以并发执行，但必须限制并发数、设置单工具超时，并按原调用位置回填结果：

不能按完成顺序追加结果，因为模型协议要求 tool result 与原 tool call 一一对应。预分配切片还有一个实际好处：每个任务只写自己的下标，不需要围绕 append 加锁，最终顺序也不受网络快慢影响。

这里的并发只适用于彼此独立的工具。如果第二个工具依赖第一个工具产生的 ID，就应由 Planner 生成两个顺序阶段，而不是强行并行。共享 map、usage 统计和事件发送要么由单 owner 管理，要么使用锁或 channel 同步；工具 goroutine 仍然不能直接写 SSE ResponseWriter。

17. 错误、取消和资源释放

SSE 建立之前的错误适合普通 HTTP 状态码，例如：

  • 400：参数错误。
  • 401：API Key 无效。
  • 403：租户或工具权限不足。
  • 409：同一会话已有活跃 turn。
  • 429：RPM 或并发配额超限。
  • 503：会话锁、模型或必要依赖不可用。

SSE 建立之后，HTTP 状态已经不能修改，应发送结构化 error 事件，并在服务端完成失败终态。

20. 落地检查清单

实现类似架构时，可以用下面的问题做最终检查：

  • 三个入口是否只负责身份和策略，而不是复制 Agent 逻辑？
  • Runtime 是否只接收可信 Principal，不读取原始 header？
  • 租户 ID 是否始终来自网关或 API Key，而不是模型参数？
  • API Key 是否使用哈希存储、精确 scope、RPM 和并发限制？
  • 持久会话是否在模型调用前创建 user/assistant 消息？
  • request_id 是否有数据库唯一约束并支持重放？
  • 同一会话是否串行、不同会话是否可以并行？
  • Redis 解锁是否校验 token？
  • 历史缓存是否带 owner、conversation 和 history version？
  • RAG 缓存 key 是否包含 tenant scope 与 index version？
  • MCP 工具是否在发现阶段和执行阶段各鉴权一次？
  • 服务端是否覆盖注入可信身份和 data scope？
  • 多工具执行是否有限流、超时、取消和稳定顺序？
  • SSE 是否只有一个 writer，并正确处理 Flush、背压和断连？
  • assistant、artifact 和 metadata 是否在 done 前进入终态？
  • 所有失败路径是否都会释放锁、配额并写入可诊断状态？

结语

构建多维调用链的关键，不是为每种调用方维护一套 Agent，而是把差异放在正确的位置：

  • 路由层区分入口。
  • 接入层建立可信身份。
  • 策略层限制知识、工具和会话能力。
  • 会话层负责幂等、锁、历史与终态。
  • Runtime 统一完成 RAG、MCP、文件任务和模型循环。
  • SSE Transport 把内部并发收敛成有序、可恢复的事件流。

当这些边界稳定后，增加新的租户类型、认证方式、检索源或 MCP 工具，通常只是扩展策略和能力实现，而不需要重写整条问答链路。
